# ADR-011: Use UUID Identifiers and Anonymous Customer Identity

## Status

Accepted

## Context

The Shopping Cart MVP allows anonymous customers to manage carts.

The product requirements also state that one customer may have only
one active cart.

Authentication and user accounts are outside the MVP.

Therefore, the backend needs a stable anonymous identifier without
introducing a full authentication system.

The system also needs identifiers for Products and Carts that can safely
be exposed through the API.

## Decision

Use UUID identifiers for:

- ProductId
- CartId
- AnonymousCustomerId

`ProductId` and `CartId` use UUID version 7 for newly generated identifiers
where practical. `AnonymousCustomerId` is a UUID version 4 generated by the
frontend.

The anonymous client retains the `AnonymousCustomerId` and sends it in the
`X-Anonymous-Customer-Id` HTTP header. The API validates the header value as
a well-formed UUID.

`POST /api/v1/carts` requires the `X-Anonymous-Customer-Id` header. The backend
uses `AnonymousCustomerId` to locate the customer's active cart.

## Anonymous Customer Flow

First visit:

Client generates UUID v4 AnonymousCustomerId
        ↓
Client stores identifier
        ↓
Client sends identifier in X-Anonymous-Customer-Id header
        ↓
Backend validates header and looks up active cart
        ↓
No active cart found: create new empty cart
        ↓
Return 201 Created with cartId, anonymousCustomerId, and ETag

Later visit:

Client retrieves stored AnonymousCustomerId
        ↓
Client sends identifier in X-Anonymous-Customer-Id header
        ↓
Backend validates header and finds existing active cart
        ↓
Return 200 OK with cartId, anonymousCustomerId, and ETag

## One Active Cart Rule

The relationship is:

AnonymousCustomerId
        ↓
      0..1
   Active Cart

When `POST /api/v1/carts` is requested with a valid `X-Anonymous-Customer-Id`
header:

1. Validate the UUID v4 value.
2. Look for an active cart for that `AnonymousCustomerId`.
3. If one exists, return it with `200 OK` and an `ETag`.
4. Otherwise create a new empty cart and return it with `201 Created`,
   a `Location` header, and an `ETag`.

## Strongly Typed Domain IDs

Domain code should not freely interchange raw Guid values.

Use strongly typed identifiers such as:

ProductId
CartId
AnonymousCustomerId

This prevents accidentally passing a ProductId where a CartId is expected.

## API Boundary

HTTP requests and responses represent identifiers as UUID strings.

`AnonymousCustomerId` travels in the `X-Anonymous-Customer-Id` request header.
`POST /api/v1/carts` requires this header. Other cart endpoints may accept it
for correlation but rely on `cartId` in the URL path.

The API layer converts header and path values into strongly typed
domain/application identifier types.

Domain objects should not depend on HTTP representation details.

## Security Boundary

AnonymousCustomerId is an identification mechanism, not authentication.

Possession of the identifier must not be treated as proof of authenticated
user identity.

Authentication and authorization will require a separate design when they
enter product scope.

## Consequences

### Positive

- No central integer ID generator is required.
- IDs can safely be generated by the application.
- IDs are suitable for API exposure.
- Strongly typed IDs reduce programming mistakes.
- Stable anonymous identity allows one-active-cart behavior.

### Negative

- The client must retain its anonymous identifier.
- Clearing browser/client storage may result in a new anonymous identity.
- Anonymous identity does not provide authentication or authorization.
- Account/cart merging will require future design when authentication is added.

## Alternatives Considered

### Database-generated integer IDs

Not selected because application-generated identifiers are easier to use
across API and domain boundaries.

### CartId only

Rejected because CartId alone does not provide a stable customer identity
for enforcing one active cart per anonymous customer.

### Authentication/UserId

Rejected because authentication and user account management are outside
the MVP.
